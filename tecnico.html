Cartão surpresa

O sistema vai integrar uma API de pagamento de terceiros que vai armazenar os dados do cartão de crédito. A LGPD e o PCI-DSS entram em choque se os dados trafegarem sem criptografia. Como a arquitetura de microsserviços de vocês isola esse risco?

O fluxo do sistema

Onde o dado entra, por onde passa, onde para

Seis saltos. Acompanhe a etiqueta em cada um: ela diz exatamente qual dado existe naquele ponto do sistema.

01

O usuário digita o cartão no app

O campo não é nosso. É um componente do SDK do gateway, renderizado dentro do app — o dado é capturado já dentro do domínio do operador certificado.

PAN + CVV + validade
02

TLS 1.3 direto do celular para o gateway

O dado sai criptografado do dispositivo e vai direto ao gateway. Não passa pelo backend do FoodFast em momento nenhum — nem de passagem, nem em log.

PAN criptografado em trânsito
03

O gateway tokeniza e devolve um identificador

O cartão fica no cofre do operador — que é quem carrega a certificação PCI-DSS e a auditoria correspondente. Voltam para nós apenas um token, a bandeira e os quatro últimos dígitos.

tok_9f8a3b7c2e · visa · 0012
04

O API Gateway do FoodFast recebe só o token

Requisição autenticada, com o token já no lugar do cartão. A partir daqui, não existe mais dado de cartão dentro do nosso perímetro.

token + id do pedido
05

Microsserviço de Pagamento — banco próprio, credencial própria

É o único serviço autorizado a falar com o gateway e o único com credencial no banco de pagamento. Nenhum outro serviço do FoodFast tem rota de rede ou senha para chegar aqui.

token, bandeira, últimos 4, status
06

O serviço de Pedidos pergunta, não consulta

Para saber se o pedido #4471 foi pago, o serviço de Pedidos chama uma API do serviço de Pagamento e recebe de volta um booleano. Ele nunca abre uma conexão com o banco de pagamento — porque não tem como.

pago: true · nada além disso

A prova no schema

A coluna que decidimos não criar

Privacy by Design não é um adjetivo que se coloca na apresentação. É uma decisão que aparece — ou não aparece — no CREATE TABLE. A nossa aparece como ausência.

pagamentos  — como quase todo mundo faria
id BIGINT PK pedido_id BIGINT FK numero_cartao VARCHAR(19) cvv VARCHAR(4) validade VARCHAR(5) titular_cartao VARCHAR(120) valor DECIMAL(10,2) status VARCHAR(20)

Quatro colunas que colocam o sistema inteiro dentro do escopo de auditoria do PCI-DSS — e que viram manchete no dia do vazamento.

pagamentos  — o nosso
id BIGINT PK pedido_id BIGINT FK token_gateway VARCHAR(64) bandeira VARCHAR(20) ultimos_quatro CHAR(4) valor DECIMAL(10,2) status VARCHAR(20) criado_em TIMESTAMPTZ

O usuário reconhece o cartão dele pelos últimos quatro dígitos. A finalidade é atendida por inteiro sem que o dado sensível exista aqui.

O tratamento de dados deve se limitar ao mínimo necessário para a realização de suas finalidades, com abrangência dos dados pertinentes, proporcionais e não excessivos.

LGPD · Art. 6º, III — princípio da necessidade

Demonstração · falha controlada

E quando a criptografia falha?

É a pergunta literal do nosso cartão. Um sistema mal desenhado, diante de uma falha, confirma o pagamento mesmo assim. O nosso trava e desfaz.

Aguardando execução.

O sistema falha fechado: nenhuma transação é confirmada sem resposta autenticada do gateway por canal criptografado. Na dúvida, o pedido permanece pendente e a transação sofre rollback — nunca o contrário.

LGPD · Art. 6º, VIII — princípio da prevenção

A pergunta que vão fazer

Se o gateway for hackeado, de quem é a culpa?

FoodFast

Controlador

Somos nós que decidimos o quê, como e por quê o dado é tratado. Não tocamos no cartão em momento nenhum — e ainda assim a decisão de cobrar, e a escolha de qual operador usar, é nossa. Art. 5º, VI.

Gateway de pagamento

Operador

Executa o tratamento seguindo as nossas instruções: guarda o cartão, tokeniza, cobra, confirma. Não define finalidade própria sobre aquele dado. Art. 5º, VII.

O controlador ou o operador que, em razão do exercício de atividade de tratamento de dados pessoais, causar a outrem dano patrimonial, moral, individual ou coletivo, é obrigado a repará-lo.

LGPD · Art. 42 — responsabilidade e ressarcimento de danos

Terceirizar o tratamento não terceiriza a responsabilidade. Se o operador vazar, o titular pode acionar o FoodFast — e a nossa defesa não é dizer que a culpa é do outro, é demonstrar as medidas que adotamos: escolha de operador certificado PCI-DSS, contrato com cláusulas de proteção de dados, TLS obrigatório, isolamento do serviço e ausência de dado sensível na nossa base.

Fundamento legal

Cada decisão técnica, e o artigo que a exige

Nenhuma escolha aqui foi feita por gosto de engenharia. Todas respondem a um dispositivo da Lei 13.709/2018.

Como isso vira processo

A decisão e a garantia de que ela sobrevive

Privacy by Design

A restrição nasce junto com o requisito

A história de usuário do módulo de pagamento não foi escrita como “o usuário cadastra o cartão”. Foi escrita já com a restrição anexada:

“O usuário cadastra a forma de pagamento — o dado deve ser tokenizado via gateway PCI-DSS, nunca persistido em texto puro, e o PAN não pode aparecer em nenhum log.”

Segurança não entrou como revisão no fim do projeto. Entrou como critério de aceite do requisito, antes da primeira linha de código.

DevSecOps

Portões automáticos, no ritmo da entrega

Entrega contínua só é segura se os controles rodarem na mesma velocidade dela. Cada commit passa por:

secret scanbloqueia o merge se uma chave de API ou algo com formato de PAN aparecer no código ou em log.
SASTanálise estática do serviço de Pagamento a cada push.
dependênciasvarredura de CVE nas bibliotecas — a porta de entrada mais comum em invasão real.
teste de authfalha o build se qualquer rota de pagamento responder sem autenticação.
menor privilégiosó o serviço de Pagamento tem rota de saída para o gateway.
